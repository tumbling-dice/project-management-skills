# Investigation Workflow

このskillは、コードやドキュメントを変更する前に、調査結果を一時コンテクストとして残すためのワークフローです。目的は、実装判断の根拠を会話だけに閉じ込めず、後続の `implementation-plan-gate` や実装作業が読める形にすることです。

## 使う場面

- 実装前に関連ファイル、既存実装、既存テストを調べたい。
- バグの原因候補や影響範囲を整理したい。
- UI / API / DB / E2E への影響を実装前に把握したい。
- 複数の実装案を比べる前に、事実と仮説を分けたい。
- ユーザーが「まだ実装しないで調べて」と依頼した。

## 使わない場面

- すでに承認済みの実装計画があり、修正を始めるだけの場合。
- コード変更、テスト追加、ファイル更新が主目的の場合。
- レビュー可能条件を判定するだけの場合。

## Template Source Rule

このskillは作業メモtemplateを所有しません。

1. 出力先PJに既存templateがある場合は、それをsource of truthとして使います。
2. PJ内templateがない場合だけ、`$project-startup-scaffold` の `assets/templates/work-context.md` をfallbackとして構造参照します。fallbackはsource of truthの代替であり、全文を機械的に複製する必要はありません。
3. fallbackも使えない場合だけ、下記「必須セクション」を最小構造として使います。

探す候補path:

- `docs/work/_template.md`
- `docs/work/template.md`
- `docs/templates/work-context.md`
- `.codex/templates/work-context.md`
- `.codex/skills/*/assets/templates/work-context.md`

fallbackを使って新しいPJ内templateを作った場合、以後はPJ内templateを優先します。template本体を変更したい場合は、出力先PJのtemplate、または `project-startup-scaffold` のtemplateを更新します。このskill内に同じ雛形を複製しません。

## 出力先

出力先はPJの慣習に従います。慣習がなければ、共有する作業文脈として `docs/work/<task-id>.md` を推奨します。共有しない個人メモなら `.work/<task-id>.md` を使ってもかまいません。チケット管理がある場合は、チケット本文またはコメントに同じ内容を残してもかまいません。

`task-id` やファイル名が指定されていない場合は、依頼内容から短い kebab-case 名を付けます。命名だけで停止しません。既存ファイルと衝突する場合は上書きせず、別名にするかユーザーへ確認します。

Codexで調査コンテクストをファイルへ作成または更新する場合は、手作業のMarkdown作成にも `apply_patch` を使います。shellのheredoc、`cat > file`、`tee` などで本文を書き込まないでください。

## 調査手順

1. 依頼内容、目的、期待動作、非対象範囲、制約を整理する。
2. ユーザーが示したファイルはヒントとして扱い、明示的な変更禁止がない限り周辺を探索する。
3. 関連ファイル、既存実装パターン、既存テストを確認する。
   - ここでいう既存テストの確認は、原則としてテストコード、fixture、設定、CI上の扱いを読むことです。
   - テスト実行は調査の必須条件ではありません。ユーザー依頼、repo手順、または原因切り分け上の必要性があり、破壊的でない場合だけ実行します。
   - テスト実行が明示されていない場合は、実行せず「既存テストは読解のみ。テスト実行は未実施」と記録すれば足ります。これは既定動作なので、テスト実行要否だけを理由に `未確認事項`、`不明瞭点`、完了報告の迷った点を増やしません。
   - テストを実行した場合も、検証完了ではなく調査上の観測結果として扱い、実装開始の承認材料にはしません。
   - `git status` や `git diff` は、既存差分の有無が調査結果に影響する場合だけ確認します。対象ディレクトリがgit repositoryでない場合は、その事実を一度記録すれば足ります。git確認不能だけを理由に `未確認事項`、`不明瞭点`、完了報告の迷った点を増やしません。
4. 関連ドキュメントを確認する。
   - 仕様、要件、設計、AI利用ルール、検証手順、review条件、作業templateに関係しそうな文書を探します。
   - 候補は `README.md`、`AGENTS.md`、`docs/project/`、`docs/ai/`、`docs/review/`、`docs/verification/`、`docs/work/`、repo固有docsです。
   - バグ原因や仕様の前提が文書と食い違う場合は、文書不整合候補として記録します。
   - 関連文書が見つからない、または不整合が見つからない場合も、その理由を `ドキュメント根拠と不整合` に残します。
5. 影響範囲を分類する。
   - API
   - UI
   - DB / migration
   - 権限 / 認証 / 認可
   - tenant
   - PII / secret / ログ
   - E2E / smoke test
   - project docs / AGENTS / verification docs
6. `事実`、`仮説`、`未確認事項` を分ける。
7. 実装に進む前に必要な人間判断と、次に調べるべきことを整理する。
8. 後続の `implementation-plan-gate` に渡す入力を明示する。

## Decision Clarificationへの接続

調査結果に人間判断待ちが複数残り、次の `implementation-plan-gate` や追加調査へ進めにくい場合は、`$decision-clarification-workflow` へ渡せるように整理します。

- 実装開始や計画作成を止めている判断
- 止めてはいないが、人間レビューで見るべきリスク
- 既存実装を追加で読むだけで解消できる事実不足
- 専門reviewやrepo内skillへroutingすべき事項

質問化が必要な場合は、調査成果物内の `実装に進む前に人間が判断する点` に、判断対象、止まっている理由、候補選択肢、推奨初期値、保留時の扱いを短く残します。すべての未確認事項を質問にせず、実装計画へ進むために必要な判断だけに絞ります。

既定では、判断質問は調査成果物内に含めます。ユーザーが独立した判断整理を求めた場合、または質問だけを別途人間に回す必要がある場合だけ、`$decision-clarification-workflow` の独立成果物として切り出します。独立成果物を求められていない場合は、調査成果物内に含めることを既定動作として扱い、それだけを理由に `不明瞭点` や完了報告の迷った点を増やしません。

## 不明瞭点に含めない既定動作

次はこのskill内で既定動作が決まっているため、人間回答が必要な `不明瞭点` や完了報告の迷った点に含めません。

- `task-id`、成果物名、出力先が未指定の場合は、依頼内容から短い kebab-case 名を付け、PJ慣習または `docs/work/<task-id>.md` を使う。
- PJ内templateがない場合は、fallback構造または必須セクションで成果物を作る。
- 対象ディレクトリがgit repositoryでない場合は、その事実を一度記録し、git確認不能だけで停止しない。
- 判断質問は、独立成果物を求められていない限り調査成果物内に含める。
- テスト実行が明示されていない場合は、既存テストを読解のみで扱い、テスト実行未実施と記録する。

人間へ返す `不明瞭点` は、実装計画へ進むために回答が必要な仕様、scope、risk acceptance、外部責務、追加調査要否に絞ります。

## 必須セクション

既存templateに不足がある場合、調査成果物側に次のセクションを追加します。template本体は勝手に変更しません。

- `調査目的`
- `依頼内容`
- `期待動作`
- `非対象範囲`
- `制約`
- `調査対象`
- `関連ファイル`
- `関連ドキュメント`
- `既存実装パターン`
- `既存テスト`
- `影響範囲`
- `ドキュメント根拠と不整合`
- `事実`
- `仮説`
- `未確認事項`
- `リスク`
- `実装に進む前に人間が判断する点`
- `次に調べるべきこと`
- `実装計画に渡す入力`

## 禁止事項

- 調査中にコード修正、テスト更新、フォーマット変更を始めない。
- 未確認事項を確定事項として扱わない。
- secrets、credential、本番DB接続情報、マスキングしていない顧客データ、本番ログの生データを成果物へ含めない。
- 調査結果だけで修正開始を承認済み扱いにしない。

## 完了報告

最後に次を報告します。

- 調査コンテクストの出力先
- 確認した主なファイル
- 確認した主なドキュメントと、文書不整合候補
- 事実、仮説、未確認事項の要約
- 実装計画に進めるかどうか
- 人間が判断する点と、`decision-clarification-workflow` へ渡す必要の有無
- 実装は行っていないこと
