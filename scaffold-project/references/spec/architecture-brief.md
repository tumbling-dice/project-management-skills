# Architecture Briefの作成手順

`docs/spec/architecture-brief.md` を作るときに使う。

## 目的

Architecture Briefは、初期の技術方針と未解決の設計判断を記録する文書である。すべての選択が確定済みであるかのようには記載しない。

## 必須セクション

- `前提`
- `技術スタック候補`
- `アプリケーション構成`
- `DB候補と判断軸`
- `認証・認可`
- `tenant分離`
- `外部連携`
- `デプロイ方式`
- `監視・ログ`
- `ローカル開発と検証`
- `すぐ決めること`
- `後で決めること`
- `人間が判断する点`

## ルール

- Architecture上の論点は、requirementsと制約から導く。
- 例に出ているだけの技術スタックを確定扱いしない。
- authentication、authorization、tenant分離、logging、secrets管理を明示的な論点として扱う。
- ユーザーが承認済み手順を示していない本番運用詳細は `要確認` とする。
- チームが未選定の場合は、早すぎる決定より判断軸を優先する。
