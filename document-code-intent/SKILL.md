# コードの意図を記録する

実装を読んだだけでは復元しにくい現在の意図を、コードに最も近いコメントへ残す。コメントの量ではなく、実装とコメントを合わせて契約を一通りに読める状態を目指す。

## 最優先規則: 作業指示を差分説明として書かない

この規則を、コメントの形式や詳しさを決める前に適用する。

ユーザーの「このようにしてほしい」という指示は、実装内容を決める authority であり、ソースコメントの本文ではない。指示を受けてコードを変更しても、変更前後の差分や今回そうしたかった理由をコメントへ書かない。

コメントには、そのコードまたは定義が現在なぜその形である必要があるかを書く。作業依頼を知らない読者にも成立する、現在形の責務、契約、不変条件、制約、設計理由へ変換して残す。

次の内容をソースコードへ記載してはならない。

- ユーザーが求めた変更内容や、依頼文の言い換え
- 「以前は A だったが B にした」のような変更前後の比較
- 今回の機能追加や修正を行った理由、作業の背景、差分の意図
- 変更前のコードが良くなかった理由や、過去の実装への評価
- 「以前は」「今回」「変更した」「修正した」など、今回の作業を前提とする説明
- `previously`、`changed`、`fixed` など、過去の実装や変更作業を主語にした説明

「何を変えたか」「なぜ今回そうしたか」は、commit message、PR 本文、Issue、review comment など、変更単位の経緯を扱う場所へ記録する。ソースコメントには、依頼や変更経緯から導かれ、現在もコードを制約する事実だけを現在形へ書き直して記載する。

```text
ユーザーの指示: 読み手が書き込み途中の JSON を読まないようにしてほしい。
悪い例: 以前は書き込み途中の JSON を読むことがあったため、原子的な置換へ変更した。
良い例: 読み手が書き込み途中の JSON を観測しないよう、同じファイルシステム内で原子的に置換する。
```

作業指示と差分説明を除くと残す情報がない場合は、そのコメント自体を追加しない。現在の契約や制約へ変換できる根拠がない場合も、推測で設計理由を作らない。

過去との互換性、移行期間中の入力、既存データ形式などが現在の挙動を制約する場合は、その制約を記載してよい。この場合も「今回変更したから」ではなく、現在受け入れる入力や維持する契約を主語にする。

## 記載規則を確定する

次の順に、コメントの対象、形式、必須項目を確認する。

1. ユーザーの依頼と、対象リポジトリの `AGENTS.md` などの作業規則
2. 対象言語の標準的な doc comment 形式と、ドキュメント生成ツールの要件
3. 変更箇所の周辺で一貫して使われている形式

上位の規則と矛盾しない範囲で既存形式を採用する。JSDoc、docstring、documentation comment など、言語やツールが解釈できる形式を使う。タグや固定テンプレートは、リポジトリ規約または生成ツールが必要とする場合だけ使う。

今回変更するソース、テスト、その変更で古くなる周辺コメントを対象にする。コメント追加だけを目的として変更していないファイルへ範囲を広げる場合は、ユーザーが明示した監査範囲に限る。生成ファイルは直接編集せず、生成元へ意図を記載する。

## コメントが必要な箇所を選ぶ

次の情報を実装だけから一通りに判断できない場合は、対象に最も近いコメントへ記載する。

- 関数、型、クラス、モジュールが担う責務と、呼び出し側へ提供する契約
- 引数、戻り値、状態の意味、単位、境界、null 値や省略値の扱い
- 例外、副作用、呼び出し順序、所有権、ライフサイクル
- 定数が表すデータと、その値を使う判断
- セキュリティ境界、並行処理、後始末、タイムアウト、キャンセルの理由
- フォールバック、優先順位、互換性、外部 API、プロトコル、ファイルシステムによる制約
- 一見単純な実装へ置き換えると破られる不変条件

公開 API には、利用者が安全に呼び出すための契約を優先して記載する。内部実装では、命名や型から分かる処理を繰り返さず、選択理由や制約を優先する。

コードを逐語的に言い換える説明や、型シグネチャと同じ情報だけを繰り返す説明は追加しない。実装に存在しない保証や、根拠を確認できない前提も記載しない。

## 定義の契約を書く

関数やメソッドには、その目的と呼び出し側が知る必要のある入出力契約を書く。引数名や型だけで意味が明らかな場合は反復せず、検証済みかどうか、許容範囲、単位、特殊値の意味を補う。戻り値がない場合も、副作用や状態遷移が契約なら記載する。

型、interface、class、module には、それが表す境界または責務を書く。member ごとの説明が必要かは、公開範囲、型から読み取れる情報、リポジトリ規約をもとに判断する。optional、nullable、判別用 member では、各状態の意味が曖昧なら明記する。

定数には、値の出所、単位、適用範囲、どの判断に使うかのうち、命名から分からない情報を書く。値を見れば分かる内容だけのコメントは付けない。

## 処理の直近に理由を書く

非自明な分岐、順序、上限、変換、後始末には、その実装が必要な理由を直前へ置く。離れた関数の説明へ埋めると変更時に同期しにくいため、制約を受ける最小の処理単位へ記載する。

外部仕様や設計文書を根拠にする場合は、リポジトリで長期利用する参照先だけを使う。リンクがなくても理解できるよう、コードを制約する事実をコメント本文にも短く残す。

## 各テストへ目的・対象・前提を書く

各テスト関数またはテスト case 定義の直前に、次の三項目をコメントで明記する。テスト名や構造から内容を推測できる場合も省略しない。

- `目的`: 保証する契約または防ぐ失敗
- `対象`: 検証する関数、境界、出力、状態遷移
- `前提`: fixture、入力状態、fake の動作など、期待値が成立する条件

対象言語の doc comment を使う。doc comment がない言語や、テストフレームワークが別の形式を要求する場合は、テスト定義へ関連付けられる block comment または line comment を使う。リポジトリが追加項目や詳細な形式を定めている場合は、その規則も満たす。

```text
/**
 * 目的: タイムアウト時に処理を停止し、分類済みエラーを返すことを保証する。
 * 対象: 実行処理のタイムアウトと終了処理。
 * 前提: fake の完了遅延が設定されたタイムアウトより長い。
 */
test ...
```

parameterized test では、テスト定義へ三項目を記載する。case 集合を定数や fixture として分離する場合は、その集合が覆う境界と選定理由も集合の近くへ記載する。各入力値を逐語的に言い換えるコメントは追加しない。

## 実装と同期する

1. 実装変更で責務、契約、前提、戻り値、優先順位が変わった箇所を特定する。
2. 古いコメントを現在の事実へ書き換え、矛盾する説明を補足で残さない。
3. 変更した定義、非自明な処理、テストを見直し、必要な意図がコードかコメントから読めるか確認する。
4. formatter、lint、型検査、unit test など、対象リポジトリが指定する検証を実行する。
5. 最終差分を読み、コメントだけが主張する保証、古い前提、自明な反復がないことを確認する。
6. 追加・変更したコメントを読み、ユーザーの指示、変更前後の比較、今回そうした理由を説明する文が残っていないことを確認する。

## 完了条件

- 対象リポジトリと言語のコメント規則に従っている。
- 変更したコードの責務、契約、非自明な制約を、実装とコメントから復元できる。
- 各テストに `目的`、`対象`、`前提`の三項目があり、保証する振る舞いと成立条件を判断できる。
- すべてのコメントが作業依頼を知らない読者にも成立し、ユーザーの指示、変更前後の比較、今回だけの差分説明を含まない。
- コメントだけを目的とした変更が、ユーザーの指定範囲を越えていない。
- 対象リポジトリが指定する検証が成功している。
