# Implementation Plan Gate

このskillは、調査済みの一時コンテクストを読み、修正開始前に人間がレビューできる実装計画を作るためのワークフローです。`status: ready` は「人間レビューへ出せる」という意味であり、人間が承認するまでコード変更を始めません。

## 使う場面

- `investigation-workflow` の結果から実装計画を作りたい。
- 調査結果をもとに、修正開始してよいか人間レビュー用に判定したい。
- 変更予定ファイル、テスト方針、検証コマンド、リスクを整理したい。
- 非自明なコード変更、権限やPIIに関わる変更、E2E影響のある変更の前に品質ゲートを置きたい。

## 使わない場面

- 調査がまだなく、関連ファイルや既存テストが不明な場合。先に `investigation-workflow` を使います。
- 承認済み計画に沿って実装する段階。
- 既存差分のレビュー可能条件だけを判定する段階。

## Template Source Rule

このskillは実装計画templateを所有しません。

1. 出力先PJに既存の実装計画template、作業メモtemplate、またはチケットtemplateがある場合は、それをsource of truthとして使います。
2. PJ内templateがない場合だけ、`$project-startup-scaffold` の `assets/templates/work-context.md` をfallbackとして構造参照し、`実装計画`、`テスト方針`、`検証コマンド` の節を中心に埋めます。fallbackはsource of truthの代替であり、全文を機械的に複製する必要はありません。現在の環境で読める場合だけ参照します。
3. fallback assetを現在の環境で読めない場合は、探し続けずに下記「必須セクション」を最小構造として使います。

PJ内templateがないこと、またはfallback assetを読めないこと自体は既定の分岐です。必須セクションで計画を作れる場合、template不在やfallback未読だけを理由に `blocked`、`未確認事項`、`不明瞭点` を増やしません。

探す候補path:

- `docs/work/_template.md`
- `docs/work/template.md`
- `docs/templates/work-context.md`
- `docs/templates/implementation-plan.md`
- `.codex/templates/work-context.md`
- `.codex/templates/implementation-plan.md`
- `.codex/skills/*/assets/templates/work-context.md`

template構造を変更したい場合は、出力先PJのtemplate、または `project-startup-scaffold` のtemplateを更新します。このskill内に同じ雛形を複製しません。

## 入力

原則として、次のいずれかを入力にします。

- `investigation-workflow` が作成した一時コンテクスト
- `docs/work/<task-id>.md` の調査メモ
- チケット本文またはコメントに残された調査結果
- ユーザーが明示した調査結果と制約

入力に不足がある場合は、計画を確定せず `status: blocked` とし、必要な追加調査を示します。

Codexで計画コンテクストをファイルへ作成または更新する場合は、手作業のMarkdown作成にも `apply_patch` を使います。shellのheredoc、`cat > file`、`tee` などで本文を書き込まないでください。

## 出力先

出力先はPJの慣習に従います。慣習がなければ、共有する計画コンテクストとして `docs/work/<task-id>-implementation-plan.md` を推奨します。入力が `docs/work/<task-id>.md` の調査メモなら、同じ `task-id` を使って実装計画だと分かる名前にします。

ユーザーが「計画コンテクストを作る」「作業メモへ残す」「後続workflowへ渡す」と依頼している場合は、ファイル作成または更新を優先します。ユーザーが会話上の提示だけを求めた場合だけ、ファイルを作らずに本文へ出力します。

`task-id` やファイル名が指定されていない場合は、依頼内容または入力調査メモ名から短い kebab-case 名を付けます。命名だけで停止しません。既存ファイルと衝突する場合は上書きせず、別名にするかユーザーへ確認します。

この命名は既定動作です。出力名が指定されていないことだけを理由に `blocked`、`未確認事項`、`不明瞭点`、完了報告の迷った点を増やしません。

## 判定手順

1. 入力コンテクストから、目的、期待動作、非対象範囲、制約を確認する。
2. 調査結果の根拠を確認する。
   - 関連ファイル
   - 既存実装パターン
   - 既存テスト
   - 影響範囲
   - `git status` や `git diff` は、既存差分の確認が必要な場合だけ使います。計画入力が調査コンテクストで、差分が前提でない場合は必須ではありません。
   - 対象ディレクトリがgit repositoryでない場合は、その事実を必要に応じて記録するだけで足ります。git確認不能だけを理由に `不明瞭点` や完了報告の迷った点を増やしません。
3. 未確認事項が実装開始を妨げるか分類する。
4. 変更方針、変更予定ファイル、テスト方針、検証コマンドを作る。
   - `status: blocked` の場合も、未確認事項の解消後に採りうる変更候補、変更予定ファイル候補、テスト候補を整理します。
   - blocked時の候補は確定計画ではありません。`要確認`、`条件付き候補`、`人間判断後に確定` のように明示し、修正開始可能な計画として扱いません。
   - 変更予定ファイルは、確定対象と条件付き候補を分けて書きます。戻り値形状や仕様判断次第で触るファイルは、条件付き候補として扱います。
   - `status: blocked` と `ready` のどちらにするかは、未確認事項が修正開始を妨げるかで決めます。`ready` の意味が「人間レビューへ出せる」であること自体は判定迷いとして扱いません。
   - 検証コマンドは、実装後に実行する候補として記載します。
   - 検証コマンドは、調査結果に書かれた候補、`package.json` などのproject manifest、CI設定、既存docsを根拠にします。これらのファイルは検証コマンドの根拠として扱い、変更予定ファイルに含めません。
   - このskillではコードやテストを変更しないため、検証コマンドは原則実行しません。ユーザーが計画作成中の確認として明示した場合だけ、調査上の観測として実行します。
   - 検証コマンドを実行しないことは既定動作なので、それだけを理由に `未確認事項` や `不明瞭点` を増やしません。
5. ドキュメントを根拠資料として確認し、不整合の扱いを決める。
   - 対象は `README.md`、`AGENTS.md`、`docs/project/`、`docs/ai/`、`docs/review/`、`docs/verification/`、`docs/work/`、repo固有docsです。
   - 実装計画の根拠にした文書、参照した節、文書上の仕様や制約を記録します。
   - バグ原因、仕様前提、検証手順、review条件、AI利用ルールが文書と食い違う場合は、コード修正計画へ進める前に扱いを決めます。
   - 文書不整合が期待動作や修正scopeに影響する場合は `status: blocked` とし、先に文書更新、人間判断、または追加調査へ戻します。
   - 文書不整合がない場合、または今回の修正判断に影響しない場合は、その理由を計画に残します。
6. 認証、認可、tenant、PII、secret、ログ、外部入力、DB、E2E影響を確認する。
7. 人間レビュー観点と、人間が判断する点を明記する。
8. 修正開始可否を `ready` / `blocked` で出す。

## Blocked時のDecision Clarification

`status: blocked` を出す場合は、長い未確認事項リストだけで終わらせず、`$decision-clarification-workflow` の考え方で `Blocked Clarification` を作ります。

- 実装計画を確定できない判断だけを3〜5個以内に絞ります。
- 各判断に、なぜblockingか、選択肢、推奨初期値、保留時の扱い、回答後に更新する計画入力を添えます。
- 追加調査で解ける事実不足と、人間が決めるべき仕様・scope・risk acceptanceを分けます。
- 未回答の質問は確定事項として扱わず、修正開始条件に含めます。

出力をファイルへ残す場合は、実装計画成果物内に `Blocked Clarification` セクションを追加します。会話上で返す場合も同じ粒度で示します。

既定では、`Blocked Clarification` は実装計画成果物内に含めます。ユーザーが独立した判断整理を求めた場合、または質問だけを別途人間に回す必要がある場合だけ、独立成果物として切り出します。独立成果物を求められていない場合は、実装計画成果物内に含めることを既定動作として扱い、それだけを理由に `不明瞭点` や完了報告の迷った点を増やしません。

## 不明瞭点に含めない既定動作

次はこのskill内で既定動作が決まっているため、人間回答が必要な `不明瞭点` や完了報告の迷った点に含めません。

- `task-id`、成果物名、出力先が未指定の場合は、入力調査メモ名または依頼内容から短い kebab-case 名を付け、PJ慣習または `docs/work/<task-id>-implementation-plan.md` を使う。
- PJ内templateがなく、必須セクションで計画成果物を作れる場合は、fallback assetを探し続けずに必須セクションで作る。
- 対象ディレクトリがgit repositoryでない場合は、その事実を一度記録し、git確認不能だけで停止しない。
- `status: blocked` の場合、`Blocked Clarification` は独立成果物を求められていない限り実装計画成果物内に含める。
- 検証コマンドは実装後候補として記載し、計画作成中に実行しない。

人間へ返す `不明瞭点` は、計画を `ready` に更新するために回答が必要な仕様、scope、risk acceptance、外部責務、追加調査要否に絞ります。

## Implementation Start Gate

このskillが判定する `ready` は、人間レビューへ出せる状態です。実装修正開始の承認ではありません。

人間レビューへ出せる条件は次の通りです。

- 目的と期待動作が明確である。
- 非対象範囲が明記されている。
- 関連ファイルを確認している。
- 既存実装パターンを確認している。
- 既存テストを確認している。
- 影響するAPI / UI / DB / 権限 / E2Eを確認している。
- 変更予定ファイルが説明されている。
- 実装計画の根拠にしたドキュメント、または関連ドキュメントがない理由が説明されている。
- 文書不整合がある場合、その扱いが説明されている。
- テスト方針が説明されている。
- 検証コマンドが説明されている。未確定なら `要確認` として扱いを明記している。
- 未確認事項とリスクが整理されている。

コード変更を始めるには、このskillの `ready` に加えて、人間が計画をレビューし、修正開始を明示承認する必要があります。

## 必須セクション

既存templateに不足がある場合、計画成果物側に次のセクションを追加します。template本体は勝手に変更しません。

- `入力コンテクスト`
- `修正開始可否`
- `変更方針`
- `変更予定ファイル`
- `ドキュメント根拠`
- `ドキュメント不整合と扱い`
- `テスト方針`
- `検証コマンド`
- `非対象範囲を守る確認`
- `未確認事項`
- `リスク`
- `人間レビュー観点`
- `人間が判断する点`
- `Blocked Clarification`（`status: blocked` の場合）
- `修正開始条件`

## statusの扱い

- `ready`: 人間レビューへ出せる状態。人間の承認前に実装してはいけません。
- `blocked`: 調査不足、未決事項、危険な前提、検証不能などにより計画を確定できない状態。

`ready` とする場合でも、承認済み計画ではなく「レビュー対象の計画」として扱います。

`blocked` とする場合は、回答が必要な判断を `decision-clarification-workflow` へ渡せる形式で整理し、人間回答後にこのskillを再実行して計画を確定します。

## 禁止事項

- 計画作成中にコード修正、テスト更新、フォーマット変更を始めない。
- 調査されていないファイルや挙動を確定事項として扱わない。
- 非対象範囲を計画に混ぜない。
- テスト削除、skip、assertion弱体化を前提にした計画を作らない。
- 認証、認可、tenant、PII、secret、ログへの影響を未確認のまま安全扱いしない。

## 完了報告

最後に次を報告します。

- 計画コンテクストの出力先
- `status: ready` / `status: blocked`
- 変更予定ファイル
- テスト方針
- 検証コマンド
- ドキュメント根拠と不整合の扱い
- 人間が判断する点
- `blocked` の場合は、回答が必要な判断質問数と次に渡すworkflow
- 修正開始には人間レビューと承認が必要であること
